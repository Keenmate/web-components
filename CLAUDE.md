# CLAUDE.md

This repo is two things:

1. **The catalogue** of KeenMate web components. `components.json` is the
   registry; the README table between the `kmwc:catalogue` markers is generated
   from it (`npm run readme`). Never hand-edit inside the markers.
2. **`@keenmate/web-components-devkit`**: the shared dev / example-site / build
   tooling every component consumes. The runtime base class and input model are
   in `../web-components-core`, not here. Nothing in this repo ships inside a
   component bundle.

## The rulebook comes first

The rules for components — structure, naming, CSS, theming, README, Custom
Elements Manifest, publishing — live in the BlissFramework rulebook:
`C:\Git\BlissFramework\guidelines\web-components\` (topic triads `.md` /
`.decisions.md` / `.checks.md` + runnable `.checks.sh`), and the JS coding
guidelines in `C:\Git\BlissFramework\web\docs\coding-guidelines-javascript\`.
The devkit **generates** what the rulebook asks for and **runs** its checks; it
never re-states or copies a rule. If a template and the rulebook disagree, the
template is wrong. If the rulebook can't see something core does (e.g. its
scripts grep for `customElements.define` / `new CustomEvent(`), keep the
pattern the scripts recognise and raise the gap — don't patch around it.

This code follows the JS guidelines too: registry verbs (`get` / `load` /
`check` / `ensure` / `map` / `generate` / `render` / `attach` / `mount` /
`handle` …), no abbreviations, `is` / `has` / `should` booleans, `config` (never
`options`) for configuration, `handle*` for internal listeners, TS type
suffixes from the closed set (`Config`, `EventDetail`, `Context`, `Spec`, …),
magic strings in a constants table.

## Why it exists

Every component repo used to carry its own copy of the example helpers, the
shared stylesheet, the Vite/Playwright configs and the deploy files. Each
session "fixed" its own copy and they drifted apart. The rule now: **a shared
concern is fixed here once and every component picks it up.** If you're in a
component repo and find a bug in a shared helper, the fix belongs in this repo.

## Layout

```
components.json          registry: catalogue, CSS prefixes, port blocks
src/config.js            package.json#kmwc → resolved config (defaults live here)
src/vite/                defineComponentConfig() + createExamplesPlugin()
  page-composer.js         fragment pages → layout, <kmwc-include>, <kmwc-demo> (pure, unit-tested)
src/playwright/          definePlaywrightConfig()
src/examples/            the kit injected into example pages
  constants.js             every class / selector / storage key the kit emits (side layer)
  auto.js                  side-effect entry (virtual:kmwc-examples)
  kit.js                   mountExamplesKit(): copy-links + chapter nav + badges + theme switch
  sections.js              THE section/slug algorithm (chapter nav + copy-link share it)
  css/                     @layer kmwc design system; tokens.css reads --base-*
src/cli/                 kmwc CLI (sync, doctor, check-vars, check-release, new, readme)
  sync-plan.js             single source for "what sync writes" = "what doctor checks"
templates/               generated-file templates, examples-layout.html, templates/new (rulebook-shaped
                         scaffold) + templates/new-minimal (overlay for --minimal)
playground/              real component made by `kmwc new`, linked via file:.. — the e2e target
test/                    node:test unit tests
```

## Rules

- **No build step.** Source is plain ESM JS, with hand-written `.d.ts` next to
  each public entry. Keep the `.d.ts` in sync when you change a signature.
- **Peer deps resolve from the component** (`getPeerModule` / `loadPeerModule`
  in `config.js`), never via a bare import in devkit code. Linked checkouts
  would otherwise load the devkit's own copy of vite/playwright, or none.
- **Kit CSS** stays inside `@layer kmwc`; feature files read only `--kmwc-*`
  tokens and colour literals live only in `tokens.css` (a unit test enforces
  it). Kit-generated classes are `kmwc-` prefixed BEM, from `constants.js`. The
  page vocabulary (`.card`, `.controls`, …) is the pages' — add, don't rename.
- **Kit mounting is deferred one task** (see `auto.js`): in builds Vite hoists
  the kit import before the page's inline script.
- **Templates:** `{{UPPER_CASE}}` placeholders only. The Makefile template uses
  real tabs. Every generated file keeps the `GENERATED by kmwc sync` header.
  `templates/new/.claude/commands/publish.md` mirrors the reference
  (`web-multiselect/.claude/commands/publish.md`) — `[canonical]` blocks stay
  byte-identical to it.
- **Ports & prefixes:** every registry entry owns one `port` block in a single
  sequence by 100, in registry order (dev = block, preview = +1, image = +10 —
  `getPortsForBlock()`); a new repo is appended and takes the next block. The
  unit tests reject gaps and collisions. No versions/status in the registry —
  they go stale.
- **Changing what a component must look like** (new standard script, new
  legacy file, new doctor check, scaffold change): update `doctor.js`, the
  README, `templates/claude-block.md` and the playground together.

## Commands

```
npm test              # unit tests
npm run test:e2e      # playground e2e — dev server AND built site (Chromium)
npm run readme        # regenerate catalogue (readme:check in CI)
cd playground && npx kmwc doctor --verbose     # every rulebook suite must be green
node src/cli/kmwc.js doctor --root ../web-<x>   # read-only check of a sibling
```

Before finishing a change to the kit or a template: `npm test`, `npm run
test:e2e` and the playground doctor must pass, and a new kit feature gets a
spec in `playground/e2e/devkit.spec.ts`. `esbuild`'s postinstall may need
`npm approve-scripts esbuild` after a fresh install.
